# Найденные проблемы и подтверждения

## Остановка pacman после проверки 651 архива

В пользовательском отчёте было 651/651 по checksum, а весь пакетный этап завершился ошибкой до появления Hyprland. Исходный отчёт упоминает `zfs-utils`. Точную последовательность событий на физическом Live USB восстановить без исходного журнала нельзя.

Механизм ошибки воспроизведён на CachyOS Live 2026.08.09 с pacman 7.1.0 и libalpm 16.0.1. Старая ветка Serpantinum добавляла `XferCommand = /usr/bin/false` в свою временную конфигурацию. Нативный solver показывал `Total Download Size: 0.00 MiB` для уже сохранённого архива `iana-etc`. При отсутствии файла подписи libalpm всё равно сформировал запрос и получил отказ внешней команды. Настройка `ParallelDownloads = 10` в конфиге Live-системы не объясняет этот отказ. [Старый код](https://github.com/zxcmadarasdaw/myo/blob/c30d39f/install/download_queue.py) · [Документация проверки](../installer/TESTS.md)

Новое решение вычисляет состав и полный архивный размер с пустым кэшем solver, проверяет содержимое по SHA-256, сверяет план перед нативным запуском и подготавливает подпись из метаданных или доступного detached-источника. Архивное имя включает версию и архитектуру. Нативный libalpm выполняет проверку и установку с отдельным временным кэшем и исходной политикой доверия. Сеть для этих двух операций ограничена локальным недоступным адресом. Оригинал использует свой нативный путь с обычным системным кэшем, поэтому его прямой вызов pacman не решает передачу отдельной очереди Serpantinum. [Код очереди](../../install/download_queue.py#L439) · [Оригинал pacman][upstream-pacman]

Отдельно воспроизведена проблема временных прав. libalpm оставлял пустой каталог, принадлежавший `DownloadUser=alpm`. Рекурсивная уборка от обычного пользователя получала EPERM и могла скрыть результат операции. Очередь использует отдельный scratch с доступом на проход и удаляет пустой каталог через `rmdir`. [Нативный запуск](../../install/download_queue.py#L533)

## Смена графических сессий

Оригинальная настройка SDDM может немедленно запустить службу. Наш установщик под systemd меняет включение службы на следующий запуск, а диагностика читает сервис и свои сессии через logind. В `serpantinumd` есть отдельный пользовательский надзор и остановка процессов оболочки. Смена пользователя в logind его напрямую не вызывает. Исходное зависание между Hyprland-сессиями не воспроизведено. Системный журнал исходного запуска недоступен, поэтому источник зависания не установлен. [SDDM оригинала][upstream-sddm] · [Наш SDDM](../../install/modules/deploy.sh#L299) · [Диагностика](../../install/modules/service.sh#L115) · [Демон](../../bin/serpantinumd#L136)
