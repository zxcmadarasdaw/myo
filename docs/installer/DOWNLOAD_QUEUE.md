# Загрузка пакетов и восстановление установки

В браузерном мастере и `bash install.sh --tui` выберите режим в настройках плана. Режим применяется к архивам pacman и DNF.

| Режим | Одновременные загрузки |
| --- | ---: |
| Stable | 1 |
| Balanced (по умолчанию) | 4 |
| Fast | 8 |
| Adaptive | 1–8, старт с 4 |

Adaptive увеличивает лимит на один после трёх последовательных секунд с положительной скоростью при полной загрузке очереди. Ошибка передачи или три последовательных замера ниже 40% недавней суммарной скорости уменьшают лимит вдвое, минимум до одного. При снижении уже активные передачи продолжаются. Следующие загрузки и повторы ждут свободного места в новом лимите. Режим остаётся Balanced по умолчанию. Скорость Adaptive зависит от последовательности размеров и зеркал, а реальный замер подтвердил более предсказуемый лимит Balanced.

## Загрузка и восстановление

1. Нативный менеджер строит полный набор пакетов с обязательными зависимостями. Кэш сверяется с размером и контрольной суммой из метаданных текущей версии.
2. Для каждой попытки curl пишет в отдельный временный файл. Текущая скорость рассчитывается по фактическому приросту файла с интервалом около 250 мс. Интерфейс одновременно показывает активные пакеты, их скорость, объём и процент при известном размере, а также суммарную скорость и счётчики очереди.
3. По умолчанию через 30 секунд без байтов появляется предупреждение, через 60 секунд останавливается только соответствующая передача. До трёх попыток с паузой 2 секунды и переходом на следующее настроенное зеркало. При ошибке места или прав файл сразу получает статус `FAILED`. Остальные передачи продолжаются.
4. После проверки checksum архив атомарно переименовывается в кэш. Незавершённые `.part` не используются как готовые архивы. При следующем запуске недокачанный или повреждённый архив загружается заново, проверенные архивы используются повторно.
5. После любой окончательной ошибки загрузки текущая транзакция блокируется. Список неудачных файлов содержит причины, последние зеркала и попытки. `Retry Failed Downloads` заново решает зависимости и повторно проверяет кэш.

Тайм-ауты можно задать при запуске. Для старого терминального мастера и прямого вызова исполнителя режим также можно задать через `SERP_DOWNLOAD_MODE`.

```bash
SERP_DOWNLOAD_WARNING=30 SERP_DOWNLOAD_TIMEOUT=60 SERP_DOWNLOAD_ATTEMPTS=3 bash install.sh
```

Требуется `0 < warning < timeout`, число попыток от 1 до 10. CLI очереди принимает `--warning`, `--timeout`, `--attempts` и `--download-mode`.

## Arch и CachyOS

Старая версия копировала конфигурацию pacman и добавляла `XferCommand = /usr/bin/false`. CachyOS Live с pacman 7.1 и libalpm 16 воспроизвёл ошибку с уже проверенным архивом и отсутствующей парной подписью. Стадия загрузки libalpm вызвала внешний процесс и получила отказ. Одной проверки SHA-256 архива было недостаточно для нативной транзакции. В новом тесте отдельно обнаружено, что libalpm оставляет пустой каталог с владельцем `DownloadUser`. Рекурсивная очистка от обычного пользователя могла получить EPERM и заменить исходный результат транзакции ошибкой очистки.

- `pacman-conf` раскрывает Include, архитектуру и политику подписей. Временная конфигурация использует встроенный libalpm и поддерживаемый `ParallelDownloads` со значением 1, 4 или 8. Для Adaptive значение при старте нативной операции равно 4. Адаптация происходит в отдельной очереди.
- `pacman -Sp --needed --print-format` решает зависимости с пустым кэшем, поэтому `%s` даёт полный размер архива. Архив идентифицируется именем, версией, репозиторием, именем файла с архитектурой и checksum. `%g` предоставляет подпись из метаданных. При отсутствии встроенной подписи проверяется кэш и выполняются ограниченные запросы detached-подписи.
- `pacman -Sw` и `pacman -S` выполняются последовательно с временной конфигурацией, где репозитории имеют только недоступный локальный источник. Нативный кэш содержит ссылки только на архивы и подписи текущего плана. libalpm применяет исходную политику подписей и архитектуры. Отдельный scratch доступен sandbox по пути, а пустые каталоги `DownloadUser` удаляются через `rmdir`.
- Пакеты и подписи сверяются при нативной проверке и установке. Системная блокировка pacman сохраняется. Кэш Serpantinum имеет отдельную блокировку между запусками.

По умолчанию используются имеющиеся согласованные базы. Ожидающие обновления блокируют обычную установку. Полное обновление требует выбранной пользователем опции `sync`: обновление metadata, разрешение **всех** обновлений через `-Spu`, предварительная очередь, `-Suw` и целая `-Su` транзакция. При неудаче после refresh базы могут быть новее установленной системы; нужно повторить полное обновление, а не выполнять выборочное `pacman -S`. Самостоятельный refresh без намерения полного обновления не запускается.

Блокировка пакетного менеджера не удаляется и не обходится. Installer не запускает параллельные pacman-команды. Изменение баз/системы между разрешением и проверкой блокирует подготовленный набор. Финальная нативная транзакция сохраняет собственные блокировки и проверки.

## Fedora

Если установлен `dnf5`, используются `libdnf5` Python API и его solver. Для DNF4 — `dnf.Base`, `fill_sack`, `resolve`, `transaction.install_set`. Из API поступают версии, репозитории, размеры, checksum, URL и нативные пути кэша. Настройки pacman сюда не переносятся. Исключения Terra из существующего адаптера передаются solver и итоговому DNF.

RPM-файлы предварительно загружаются общей очередью. Перед установкой выполняются checksum и `rpmkeys --checksig` с системным набором доверенных ключей. После этого заполнен нативный кэш DNF, а `dnf --cacheonly install/upgrade` запускается с **исходными целями**, сохраняя причину установки зависимостей и политику GPG репозиториев. Cache-only запрещает дополнительные сетевые загрузки на этой стадии. Нет `--skip-broken`, отключения зависимостей или отключения подписей в новом пути.

Если не хватает Python или соответствующего DNF API, существующий bootstrap предлагает явно подтверждаемую небольшую нативную транзакцию (`python`/`python3`, `python3-libdnf5` либо `python3-dnf`). Для неё также установлен один поток загрузки. Это подготовка среды до запуска структурированной очереди; подробный прогресс самой очереди начинается после неё.

Недостающий ключ COPR нужно получить и проверить через доверенный процесс настройки репозитория. Очередь не помечает неизвестный ключ как доверенный. Существующие отдельные операции настройки COPR/Terra, upstream-бинарники, шрифты, AUR и VPN-комплект сохраняют свои отдельные сценарии; они не представлены как RPM/pacman-файлы этой очереди.

## Кэш, журнал и восстановление

Архивы хранятся в `${XDG_CACHE_HOME:-$HOME/.cache}/serpantinum-installer/packages/{pacman,dnf}`. Для Live USB проверьте, что каталог находится на постоянном носителе, если он должен пережить выключение. Интерфейс показывает свободное место кэша и временного каталога. Нативный менеджер проверяет место под установку.

Приватный журнал и TXT/JSON-отчёты сохраняются в каталоге состояния Serpantinum. Отчёт ведёт отдельные результаты загрузки, нативной проверки и установки для каждой пакетной транзакции. Проверка системной интеграции и фактически найденный Hyprland показаны отдельно. Сохранённый план появляется при следующем запуске. После его повторного просмотра и подтверждения мастер начинает с последней незавершённой фазы в пределах текущей загрузки ОС. После перезагрузки он снова проверяет план с первой фазы. Наличие каталога кэша проверяется при восстановлении, архивы проверяются по метаданным при загрузке.

## Графическая сессия

Проверка установленного Hyprland проверяет бинарник, совместимость Lua-конфигурации и наличие записи в `wayland-sessions`. План с конфигурацией перед установкой проверяет совместимость Hyprland и позже разворачивает файлы для выбранной сессии. Причину зависания исходной сессии пользователя установить без её системного журнала не удалось. Проверка кода установщика показала, что смена конфигурации дисплейного менеджера в systemd включает службу для следующего запуска и не останавливает текущую сессию.

Если после смены пользователя рабочий стол недоступен, откройте TTY сочетанием Ctrl+Alt+F3, войдите под своим пользователем и выполните `bash install.sh --session-check`. Команда показывает состояние дисплейного менеджера и ваши сессии. Для возврата используйте `bash install.sh --return-session ID`, указав ID своей сессии Wayland или X11. Команда активирует локальную сессию через logind, сохраняя другие сессии. Журнал текущего запуска доступен через `journalctl -b -u display-manager.service` и `journalctl --user -b`.
