# Последовательная очередь пакетов

Изменения от 18 ноября 2026 года. Основной запуск: `bash install.sh`, терминальный менеджер: `bash install.sh --tui`.

## Что изменено

Ранее `pm_pacman_install` вызывал обычный `pacman -S`/`-Syu`, наследуя системный `ParallelDownloads`. DNF также наследовал параллелизм своего загрузчика. GUI пытался извлекать размер, скорость и проценты из терминальных строк. Наблюдение за выводом или CPU дочернего процесса не определяло отсутствие прогресса конкретного файла.

Теперь `install/download_queue.py` предварительно скачивает разрешённый набор пакетов, строго по одному файлу. Разрешение зависимостей, политика репозиториев, проверка подписей и установка остаются у системного пакетного менеджера. Нет отдельных установочных транзакций для каждого файла очереди.

Сохранены существующие страницы, цвета, план, выбор компонентов, журнал, ввод sudo, фазы, отмена и восстановление. Дополнительно показаны текущие имя/версия/репозиторий, размер и полученные байты, процент, текущая и средняя скорость, ETA, позиция, счётчики, суммарная полоса, зеркало и раскрываемые строки очереди.

## Загрузка и восстановление

Состояния: `QUEUED`, `CHECKING`, `DOWNLOADING`, `DOWNLOADED`, `VERIFYING`, `VERIFIED`, `RETRYING`, `DEFERRED`, `FAILED`, `INSTALLED`.

1. Системный solver строит весь набор, включая необходимые зависимости.
2. Проверяется существующий кэш. Подходящие файлы повторно хешируются; успешные загрузки сохраняются между запусками.
3. Curl записывает один `.part` без буферизации. Счётчик измеряет размер именно этого файла каждые 250 мс. Сетевые счётчики компьютера и текстовые проценты не используются.
4. Текущая скорость = прирост байтов / интервал; средняя = байты / длительность попытки. ETA показывается только при известном размере и положительной текущей скорости. Неизвестный размер даёт неопределённую полосу текущего файла.
5. Нулевой прирост допустим. Через 30 секунд отсутствия прироста появляется предупреждение; через 60 секунд процесс загрузки останавливается. Выполняется ограниченная HEAD-диагностика соединения; её результат отражается в подробностях ошибки. Сначала прекращается основной запрос, затем выполняется диагностика.
6. Всего по умолчанию три попытки, с паузой 2 секунды. При наличии используются последующие зеркала из тех же настроенных репозиториев. Нехватка места и запрет записи прекращают попытки этого файла сразу. После исчерпания попыток пакет получает `FAILED`, а очередь переходит к следующему.
7. SHA-256 pacman или checksum из DNF metadata проверяется до атомарного сохранения файла. `VERIFIED` на стадии загрузки означает проверенный checksum, а не самостоятельное утверждение о доверии к ключу. Нативная проверка подписей обязательна перед изменением системы.
8. При любом недостающем файле блокируется соответствующая целая транзакция. Успешные файлы остаются в кэше. Завершённые ранее самостоятельные транзакции не откатываются.

`Retry Failed Downloads` повторяет неудачную фазу утверждённого плана. Solver заново проверяет состояние системы; проверенные файлы того же содержимого берутся из кэша. Новые версии, изменившиеся после обновления metadata, требуют новой загрузки. Установка продолжается только после полного успешного набора и нативных проверок.

Настройки передаются окружением при запуске:

```bash
SERP_DOWNLOAD_WARNING=30 SERP_DOWNLOAD_TIMEOUT=60 SERP_DOWNLOAD_ATTEMPTS=3 bash install.sh
```

Требуется `0 < warning < timeout`, все интервалы конечны; число попыток от 1 до 10. CLI исполнителя также принимает `--warning`, `--timeout`, `--attempts`. Таймер загрузки работает только внутри curl: подписи, распаковка, RPM-транзакция и AUR-сборка под него не попадают.

## Arch / CachyOS

`pacman-conf` выдаёт развёрнутую конфигурацию с Include, Server, репозиториями CachyOS, архитектурой и SigLevel. Её временная копия содержит `ParallelDownloads = 1`. Системная конфигурация и зеркала не меняются.

`pacman -Sp --needed --print-format` выдаёт структурированные поля `%n`, `%v`, `%r`, `%s`, `%f`, `%h`, `%l`. Это разрешённая транзакция, а не список одних явно запрошенных пакетов. Curl работает по этим данным; дополнительные зеркала берутся через `pacman-conf --repo ... Server`.

После предварительной очереди повторно сверяются имя, версия, репозиторий и checksum всего набора. `pacman -Sw` выполняет нативную стадию download-only; окончательный `pacman -S` снова проверяет зависимости, подписи, конфликты и место. Оба используют тот же staging-кэш и `XferCommand = /usr/bin/false`: отсутствующий файл не может незаметно запустить дополнительную загрузку на этапе установки. Запросы итоговой транзакции остаются в существующем интерактивном журнале.

По умолчанию используются имеющиеся согласованные базы. Ожидающие обновления блокируют обычную установку. Полное обновление требует выбранной пользователем опции `sync`: обновление metadata, разрешение **всех** обновлений через `-Spu`, предварительная очередь, `-Suw` и целая `-Su` транзакция. При неудаче после refresh базы могут быть новее установленной системы; нужно повторить полное обновление, а не выполнять выборочное `pacman -S`. Самостоятельный refresh без намерения полного обновления не запускается.

Блокировка пакетного менеджера не удаляется и не обходится. Installer не запускает параллельные pacman-команды. Изменение баз/системы между разрешением и проверкой блокирует подготовленный набор. Финальная нативная транзакция сохраняет собственные блокировки и проверки.

## Fedora

Если установлен `dnf5`, используются `libdnf5` Python API и его solver. Для DNF4 — `dnf.Base`, `fill_sack`, `resolve`, `transaction.install_set`. Из API поступают версии, репозитории, размеры, checksum, URL и нативные пути кэша. Настройки pacman сюда не переносятся. Исключения Terra из существующего адаптера передаются solver и итоговому DNF.

RPM-файлы предварительно загружаются общей очередью. Перед установкой выполняются checksum и `rpmkeys --checksig` с системным набором доверенных ключей. После этого заполнен нативный кэш DNF, а `dnf --cacheonly install/upgrade` запускается с **исходными целями**, сохраняя причину установки зависимостей и политику GPG репозиториев. Cache-only запрещает дополнительные сетевые загрузки на этой стадии. Нет `--skip-broken`, отключения зависимостей или отключения подписей в новом пути.

Если не хватает Python или соответствующего DNF API, существующий bootstrap предлагает явно подтверждаемую небольшую нативную транзакцию (`python`/`python3`, `python3-libdnf5` либо `python3-dnf`). Для неё также установлен один поток загрузки. Это подготовка среды до запуска структурированной очереди; подробный прогресс самой очереди начинается после неё.

Недостающий ключ COPR нужно получить и проверить через доверенный процесс настройки репозитория. Очередь не помечает неизвестный ключ как доверенный. Существующие отдельные операции настройки COPR/Terra, upstream-бинарники, шрифты, AUR и VPN-комплект сохраняют свои отдельные сценарии; они не представлены как RPM/pacman-файлы этой очереди.

## Кэш, Live и отчёты

Кэш: `${XDG_CACHE_HOME:-$HOME/.cache}/serpantinum-installer/packages/{pacman,dnf}`. Системные кэши читаются и проверяются, но не очищаются. Для DNF дополнительно оценивается место под копию в нативном кэше. До очереди показаны путь кэша, требуемый объём, свободное место, временный каталог и его свободное место; на Linux также доступная RAM. Перед каждым файлом проверяется размер плюс запас 16 MiB. Нативный менеджер отдельно проверяет пространство для установки и распаковки.

Проверки Live из основного установщика сохранены. Никакие операции с SSD-разделами, автоматическое расширение overlay или полное обновление Live без выбора пользователя не выполняются. RAM и overlay не складываются как независимые ресурсы: нехватка tmpfs/overlay может потребовать другой загрузочной среды или освобождения места.

Итоговый отчёт открывается в окне автоматически. Экспорт даёт TXT и JSON; оба также автоматически сохраняются рядом с частным журналом как `install.*.log.report.txt/json`. Отчёт содержит все пакетные транзакции данного запуска, состояния, версии, checksum, полученные байты, причины, попытки и имена зеркал. URL с учётными данными, путями подписок и query-токенами исключаются; raw-журнал в экспорт отчёта не включается. Сам журнал доступен отдельной существующей кнопкой.

Ошибки различаются: timeout, DNS, reset, HTTP 404/403, TLS, подпись, checksum, место, зеркало, зависимости, отсутствие пакета, права, отмена и неизвестная ошибка. Если solver не смог построить транзакцию, отображается ошибка плана без вымышленных пакетов и размеров.

## Проверка и ограничения

См. [TESTS.md](TESTS.md). Новая очередь 18 ноября проверена на Windows с mock-адаптерами и настоящим curl к локальному HTTP-серверу. GUI проверен браузером на явно обозначенной синтетической fixture. **Новая реализация не проходила установку на настоящих CachyOS, CachyOS Live или Fedora.** Предыдущие Linux-результаты от 17 ноября относятся к прежнему пакетному пути.

Обязательна приёмка на целевых ОС: нативный DNF4/5 cache-only layout, ключи COPR, download-only pacman с установленной версией libalpm, реальные зеркала и подписи, полная группа зависимостей, прерывание сети и ограниченная overlay. Curl использует доступные URL metadata; специальные настройки прокси/клиентского TLS из конфигурации нестандартного загрузчика pacman/DNF требуют отдельной проверки. Неподдерживаемые или недоступные metadata блокируют установку, а не переключают её на непроверенный путь.
